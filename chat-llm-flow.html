Chat 對話：詢問 LLM 的完整流程

對象功能：前端「智能對話」頁（Chat.jsx），呼叫後端 GET /api/ai/rag/agent。這是目前唯一會用到向量資料庫（rag_documents 表）的功能， 但屬於工具觸發式檢索——由 LLM 自行決定要不要查，而非每則訊息都查。

逐步解釋

  1. 前端送出：chatAgent(query, conversationId) 打 GET /api/ai/rag/agent。conversationId 由整個瀏覽器分頁共用，讓多輪對話能延續。
  2. 載入對話記憶：MessageChatMemoryAdvisor 依 conversationId 從 ChatMemory 撈出歷史訊息，接在這次訊息前面。
  3. 組提示詞：RagController 指定系統提示（「你是誠邑建築公司的招聘助手，需要履歷內容時呼叫 resumeSearchFunction，多位候選人分別查一次」），加上使用者這次的問題。
  4. 第 1 次呼叫 LLM：連同兩個工具的定義（resumeSearchFunction、recruitServiceFunction）一起送給 Groq 上的 chat 模型。
  5. LLM 決定要不要查：
    • 問題牽涉履歷（例：某人的專長、年資、是否符合職缺）→ LLM 回傳一個「工具呼叫」，並自己決定關鍵字（可能是「林敬堯」或「林敬堯 專長」，程式沒有寫死）。
    • 一般閒聊或非招聘問題 → LLM 不呼叫工具，直接作答，完全不碰向量庫。
  6. 執行工具 = 向量搜尋：
    • ResumeSearchFunction 拿到關鍵字字串。
    • PgVectorStore.similaritySearch() 先呼叫 Ollama embedding 模型把這個關鍵字轉成 1024 維向量——這一步才是「把字串向量化」。
    • 用這個向量對 rag_documents 表下 SQL：ORDER BY embedding <=> 查詢向量（pgvector 的 cosine 距離運算子），取最接近的前幾筆，並過濾相似度門檻。
    • 回傳這些履歷片段的原文。
  7. 片段回饋給 LLM：Spring AI 把工具結果附回對話。
  8. 第 2 次呼叫 LLM：LLM 讀履歷片段，整理成人看得懂的答案（例：「林敬堯的專長是結構設計與 BIM……」）。
  9. 寫回記憶：這次的問題與回答存進 ChatMemory，供下一輪使用。
  10. 回傳前端：純文字，無結構化來源欄位；前端直接把文字貼進對話泡泡。
重點澄清：被向量化的是「LLM 決定丟給工具的關鍵字」，不是你原本那句完整問題。 整個過程 LLM 被呼叫兩次：第一次決定查什麼、第二次根據結果作答。
